# 并行约束 + 仲裁器 架构设计

> 版本: v1.0 | 状态: 提案（未实现） | 日期: 2026-08-14
> 涉及: PathFollower / PathPlanning / NormalScene / CarScene / PersonScene / TrafficSignScene / DetectionTask / SceneManager / SharedContext
> 核心变化: **从"互斥单场景状态机"改为"常驻约束层 + 仲裁器"**，根治"每加一个场景效果差一档"

## 1. 背景：现有架构的四大弊端

当前架构是「互斥单场景状态机」——同一时刻只有一个场景对象活着，DetectionTask 每帧取"图像最下方目标"决定切哪个场景，场景之间通过 `SharedContext` 里的全局标量互相影响。

| # | 弊端 | 表现 | 根源 |
|---|------|------|------|
| 1 | 场景互斥 vs 障碍共存 | CarScene 激活时不看 person（撞人）；PersonScene 激活时不看 car（绕不过） | 单场景只能对单一目标类型反应 |
| 2 | 决策启发式脆弱 | "取 y2 最大目标" + `lost_frame_limit` 缓冲 → 切换滞后 | 决策与执行分属两线程 + 缓冲 |
| 3 | 切换丢状态 | `switchTo` 新建对象丢 `last_error/speed/edge`，靠 `first_frame_` 继承补 | 补丁摞补丁 |
| 4 | 单一标量无法表达多约束 | `target_speed/steering_pwm` 两个标量，无法叠加多个障碍干预 | 单一场景写死一个约束 |

**核心判断**：`follow_edge_global` 被 CarScene（避障语义）和 TrafficSignScene（岔路语义）两个场景以不同语义写入，NormalScene 首帧盲读——这是 traffic 拖累全局的直接证据。Car/Person 碰巧是"单个简单约束"所以污染小，Traffic 是"多阶段+持久决策+倒车盲开"的复杂约束，一进来就搅乱全局。

## 2. 新架构总览

```
                        ┌──────────────────────────────────────┐
                        │   DetectionTask（只发检测结果，不再切场景） │
                        │     det_result.publish()               │
                        └────────────────┬─────────────────────┘
                                         │ 各约束层读 det_result
      ┌──────────────┬───────────────────┼───────────────┬──────────────┐
      ▼              ▼                   ▼               ▼              ▼
  PersonConstraint CarConstraint    SignConstraint   基础巡线层（常驻）
  "人到了→速度0"  "车在左→边界右"   "路牌→停/倒/盲开"  PathFollower.process
      │              │                   │               │
      │           每帧产出 Constraint（可空）            │ 基础 speed/pwm/edge
      └──────────────┴───────────────────┴───────────────┴──────────────┘
                                         ▼
                              ┌────────────────────┐
                              │    仲裁器 (Arbiter)  │
                              │ 合并约束 → 最终输出    │
                              └────────┬───────────┘
                                       ▼
                                UART sendControl
```

**三个关键变化**：

1. **约束层是常驻对象**（不是每次切换新建）→ 私有状态天然持久，`traffic_decision` 不用放全局。
2. **基础巡线层永远在跑** → 无切换、无 `first_frame_` 继承、控制连续。
3. **没有 `switchTo` / `hold` / `release`** → 障碍干预只是"约束的添加与撤销"，天然可叠加。

## 3. 三层结构详解

### 3.1 基础巡线层（常驻）

就是现在的 `PathFollower::process`，几乎不动。职责：**只回答"没有障碍时该怎么走"**。

```
输入：seg_mask + 当前生效边界 edge（仲裁器喂入）
输出：基础 steering_pwm + 基础 target_speed
```

关键改动：`follow_edge_` 不再是 `PathFollower` 自己继承/决定的私有状态，而是**仲裁器每帧喂入的输入**。基础层不关心边界从哪来，只按给定的 edge 巡线。

### 3.2 约束层（3 个常驻对象）

每个约束层独立读 `det_result` + 维护自己的状态机，每帧产出 0 或 1 个 `Constraint`。无目标时产出空约束。

### 3.3 仲裁器（Arbiter，纯函数）

```
输入：基础输出 + 约束列表
输出：最终 speed / pwm / edge
```

## 4. Constraint 数据结构

```cpp
struct Constraint {
    bool  takeover;        // 独占接管（traffic 倒车/盲开），期间无视其他约束
    float takeover_speed;  // 接管速度（倒车负 / 盲开固定）
    float takeover_pwm;    // 接管转向（倒车回正 / 盲开满舵）
    bool  has_speed;       // 是否干预速度（软约束，可叠加）
    float speed;           // 要求速度（0=停）
    bool  has_edge;        // 是否干预边界（软约束，可叠加）
    int   edge;            // -1左 +1右
    int   edge_priority;   // 边界冲突裁决：避障=2 > 岔路=1（速度维度不用它）
};
```

## 5. 仲裁规则（三条，不是"优先级排序"）

**规则 1：独占接管** —— 有 `takeover=true` 的约束，直接执行它的 `takeover_speed` + `takeover_pwm`，无视其他一切。traffic 倒车、盲开用这条（天然排他）。

**规则 2：速度维度合并** —— 无接管时，所有要求速度的约束取最小值：

```
最终速度 = min( 基础速度, 所有 has_speed 约束的速度 )
```

停车(0)天然压过一切，倒车(负)更压。这是**叠加**，不是"谁赢"。

**规则 3：边界维度合并** —— car（避障）和 sign（岔路）可能同时要求边界，正常同向（都走对侧/都走右）。只有罕见冲突时按 `edge_priority` 裁决：**避障(2) > 岔路(1) > 基础边界(默认左)**。

关键：**速度用 min、边界同向叠加，car 和 person 天然并行，不需要"选一个"**。

## 6. 核心洞察：正交叠加 + 独占抢占

一张图（视野）会同时出现多个元素 → 多个约束同时产出。但它们的处理方式分两类：

### 6.1 car 和 person 能同时处理（正交叠加）

因为它们管的是**不同维度**：

| 约束 | 管哪个维度 | 值 |
|------|-----------|-----|
| CarConstraint | **边界**（转向） | 障碍在左 → 边界切右 |
| PersonConstraint | **速度** | 人到了 → 速度=0 |

一个管"往哪拐"，一个管"多快"，**天然并行，互不冲突**：

```
视野里同时有：左侧一辆车 + 前方一个人
  car    约束 → 边界 = 右
  person 约束 → 速度 = 0
  ─────────────────────────────
  合并：车贴着右边界，但速度 0（停下等人）
  人让开 → person 约束撤销 → 速度恢复 → 继续沿右边界绕车
```

这就是"同时处理"——不需要任何优先级，两个约束叠加就行。

### 6.2 traffic 做不到同时处理（独占抢占）

因为 traffic 的倒车、盲开不是"改某个维度"，而是**整个控制权接管**：

- 倒车：强制速度 -0.1 + 舵回正，期间不能同时避障
- 盲开：强制满舵 + 固定速度，期间不能同时停车

它是**独占式**的，天然排他。所以 traffic 期间其他约束让路——这是"独占 vs 叠加"的本质区别，不是"优先级高低"。

### 6.3 两个漏洞怎么被解决

- **撞人**：车在侧方(改边界) + 前方有人(改速度) → 速度 `min=0` 先停；人让开后速度恢复，边界仍被 car 约束切对侧 → 自然接着绕车。
- **绕不过 car**：人让开（停车约束撤销）后，car 约束还在 → 边界切对侧 → 绕过去。

## 7. 场景迁移映射

### 7.1 NormalScene → 基础巡线层

- 保留 `follower_.process` 全逻辑。
- 删除：`follow_edge_` 的全局继承（改由仲裁器喂入）。
- 等宽处理 `normalizeTrackWidth` 的归属待定（见 §9 待拍板点 4）。

### 7.2 CarScene → CarConstraint

| 保留 | 丢弃 |
|------|------|
| `findCarBox` / `boxToBird` / `trackCenterXAt` / 避障方向判断 | `follower_.process`（不再自己巡线） |
| 实时检测每帧判左右 | 写 `follow_edge_global`（改为产出 edge 约束） |

```cpp
// CarConstraint::tick(ctx)
DetectionBox box;
if (findCarBox(ctx, box)) {
    cv::Point2f obs = boxToBird(box, ctx);
    float center = trackCenterXAt(seg_mask, obs.y, ctx);
    int edge = (obs.x < center) ? 1 : -1;   // 障碍在左→右边界
    return Constraint{ .has_edge=true, .edge=edge, .edge_priority=2 };
}
return {};  // 无车 → 空约束
```

### 7.3 PersonScene → PersonConstraint

| 保留 | 丢弃 |
|------|------|
| `findPersonBox` / `boxToBird` / `stopped_` / `shouldGo` / 运动方向判断 | `follower_.process` |
| 停车/起步状态机 | 直接 `sendControl`（改为产出 speed 约束） |

```cpp
// PersonConstraint::tick(ctx)
DetectionBox box;
if (findPersonBox(ctx, box)) {
    cv::Point2f obs = boxToBird(box, ctx);
    updateMotion(obs);
    float stop_y = birdH() * sp.person_stop_ratio;
    if (obs.y >= stop_y) stopped_ = true;
    if (stopped_ && shouldGo(obs, trackCenterXAt(...))) stopped_ = false;
} else {
    if (++lost_frames_ > kResume) stopped_ = false;
}
if (stopped_)
    return Constraint{ .has_speed=true, .speed=0.0f };   // 速度维度不用优先级
return {};  // 没停 → 空约束（不干预巡线）
```

### 7.4 TrafficSignScene → SignConstraint（重点）

现有四阶段状态机映射到约束产出：

| 现有状态 | SignConstraint 内部状态 | 每帧产出的 Constraint |
|---------|------------------------|---------------------|
| APPROACH（巡线接近） | `IDLE` / `APPROACHING` | 空（让基础巡线跑，默认右边界接近路牌） |
| 稳定+延时到位 | `TRIGGERED` | 停车 + 发 VLM（异步），进入倒车 |
| BACKUP（倒车） | `BACKING` | `takeover=true, takeover_speed=-backup_speed, takeover_pwm=neutral` |
| WAIT_VLM（停车等） | `WAITING` | `has_speed=true, speed=0` |
| DRIVE 右转盲开 | `BLINDING` | `takeover=true, takeover_speed=turn_blind_speed, takeover_pwm=满舵` |
| DRIVE 右转巡线 | `RIGHT_EDGE` | `has_edge=true, edge=+1` |
| DRIVE 直走巡线 | `STRAIGHT` | `has_edge=true, edge=-1`（或空，用默认左） |

**关键**：`decision_` 变成 `SignConstraint` 的**私有成员**（`int decision_ = -1`），常驻 → 跨圈持久，且**不污染全局**。VLM 返回后写 `decision_ = (r==1 ? 0 : 1)`（反值，存"下一次方向"），下次 `TRIGGERED` 时若 `decision_>=0` 直接跳过 VLM、复用决策，但倒车/盲开仍走。

## 8. 状态归属对比（根治污染）

| 状态 | 现在放哪（乱） | 新架构放哪（干净） |
|------|--------------|------------------|
| `follow_edge_global` | SharedContext（Car/Traffic 双写者语义冲突） | **删除**。边界由仲裁器每帧合成 |
| `traffic_decision` | SharedContext | SignConstraint 私有成员 |
| `last_error` / `target_speed` | SharedContext | 基础巡线层私有（常驻，无需跨层继承） |
| `car_edge` / 障碍点 | SharedContext（HUD 显示） | 保留，仅显示，不参与控制 |

## 9. 等宽处理的归属

`normalizeTrackWidth` 现在无条件对所有场景生效，是 traffic 岔路被裁的根子。新架构里它应该**收敛到基础巡线层内部，或按边界条件触发**（本提案不展开，需单独定：等宽是"基础巡线的一部分"还是"某类赛道的可选步骤"）。列为待拍板点 4。

## 10. 组件增删

**删除**：
- `SceneManager.switchTo / hold / release`
- `DetectionTask` 里的 `scene_map` 查找 + 切换逻辑
- `SceneFactory` / `REGISTER_SCENE`（约束层是常驻组件，直接实例化）

**新增**：
- `Constraint` 结构体
- `PersonConstraint` / `CarConstraint` / `SignConstraint`（三个常驻类）
- `Arbiter`（纯函数：`(基础输出, 约束列表) → 最终输出`）

**保留**：
- `PathFollower`（基础巡线核心，小改）
- `PathPlanning`（算法，不动）
- `RKNNEngine` / 采集 / 分割 / 检测（不动）

## 11. 迁移步骤（分阶段，每阶段可独立验证）

| 阶段 | 内容 | 验证标准 |
|------|------|---------|
| P0 | 抽出 `Constraint` + `Arbiter` 骨架，Normal 巡线作为基础层跑通 | 纯巡线和现在一致 |
| P1 | CarScene → CarConstraint，仲裁器合并边界 | 单车避障 = 现在 CarScene 效果 |
| P2 | PersonScene → PersonConstraint，仲裁器合并速度 | 单人停车 = 现在 PersonScene 效果 |
| P3 | **同时有人有车**（你当前撞车场景） | 先停后绕，不再撞/不再卡 |
| P4 | TrafficSignScene → SignConstraint（含 VLM/倒车/盲开/持久决策） | 岔路行为 = 现在 Traffic 效果 |
| P5 | 删 `SceneManager`/`SceneFactory`/DetTask 切换逻辑 | 全场景 + 多障碍并发稳定 |

P0–P2 是低风险重构（行为等价）；P3 是**核心价值验证点**；P4 风险最高（Traffic 逻辑最复杂）；P5 是清理。

## 12. 待拍板点（实现前需你定）

1. **边界冲突裁决**：避障(2) > 岔路(1) 是否够用？有没有其他边界冲突场景需要额外规则。
2. **Sign 停车识别 VLM 期间**：用硬接管独占（期间无视行人）？还是仍让行人停车约束生效？
3. **Sign 右转的边界**：右转"走右边界"是软约束（可和避障共存），但"盲开"必须硬接管——这个分界要明确。
4. **等宽处理**：归基础巡线层，还是做成"按边界/场景条件触发"？
5. **DisplayTask / HUD**：场景名、vlm_state 等显示信息在无场景概念后怎么呈现（需要新的"当前生效约束"展示）。

## 13. 结论

这套架构把"障碍"从"互斥场景"改成"并行约束层"，根治了"每加一个场景效果差一档"的结构病——之后每加一个障碍类型 = 加一个约束层，互不污染。代价是一次大重构（删 SceneManager、改 DetectionTask、三个场景重写）。

建议先做 P0–P3 最小可行验证（Car + Person 两个约束层 + 仲裁器），在真实赛道确认"同时有人又有车"是否真解决，再决定是否投入 P4 迁移 Traffic。
